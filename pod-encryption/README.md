# Pod encryption fixtures and vectors

Cross-implementation fixtures for the Cascade Pod encryption format, specified in the `spec` repository's [`pod-encryption.md`](https://github.com/the-cascade-protocol/spec/blob/main/pod-encryption.md). Section numbers below refer to that document.

Everything here is synthetic. No file holds personal or health data: the sealed plaintexts are one-line Turtle comments and one synthetic medication record with a `urn:uuid:` identifier.

## The keys are TEST-ONLY

Every passphrase in this directory protects nothing but these fixtures, and is published on purpose. **Never use one for a real Pod.**

| Key | Opens |
|---|---|
| `conformance-passphrase-do-not-reuse` | `positive/ts-produced-v1.0`, `positive/rust-produced-v1.0`, and every vector built from them |
| `copper velvet orbit lantern mossy quartz` (key A) | `positive/rust-produced-v1.1/single`, the first wrap of `positive/rust-produced-v1.1/two-wrap`, and every vector built from them. It was the key of `positive/ts-produced-v1.1/pod` **before** its re-wrap and must no longer open it. |
| `birch meadow anchor violet copper lantern` (key B) | the second wrap of `positive/rust-produced-v1.1/two-wrap`, and `positive/ts-produced-v1.1/pod` |

The salts of the four envelope fixtures are fixed values, not random ones, so the fixtures are reproducible. Writers must use random salts (section 6.2); readers cannot tell the difference and must not try.

## Positive fixtures: what each proves

The bytes are frozen. When a test against them fails, an implementation has drifted; the fixture is not stale. Two independent implementations wrote them, and each reads the other's.

| Fixture | Written by | Proves |
|---|---|---|
| `positive/ts-produced-v1.0/` | the TypeScript reference tool (`cascade-cli`) | a reader opens a version 1.0 header and a sealed resource written by the TypeScript implementation |
| `positive/rust-produced-v1.0/` | an independent Rust implementation | the same for the Rust implementation's output |
| `positive/rust-produced-v1.1/single/` | Rust | a version 1.1 header: one passphrase wrap carrying its own KDF parameters |
| `positive/rust-produced-v1.1/two-wrap/` | Rust | two wraps of one data key with distinct salts; either key opens it, and key B is reached only by trying wraps in order (section 5.5) |
| `positive/ts-produced-v1.1/pod/` | `cascade-cli` | a whole encrypted Pod as a writer leaves it: every file sealed except `README.md` and the header (section 3.2), `.well-known/solid` and `settings/preferences` sealed although they are not Turtle, and a version 1.0 header migrated to 1.1 by a re-wrap from key A to key B (section 6.5). Key B opens it; key A must be refused as an incorrect secret. |

The four envelope fixtures each hold `encryption.json` (the header), `resource.bin` (one sealed resource, `nonce(12) || ciphertext || tag(16)`) and `plaintext.txt` (exactly what `resource.bin` decrypts to). The Argon2id parameters are the real ones writers use (`t = 3`, `m = 65536`, `p = 1`), not cheap test values: the KDF is where two implementations drift, and a fixture with cheap parameters would guard nothing.

## Vectors

`vectors.json` lists every fixture and vector with its expected outcome (section 5.4). It, and every file under `negative/` and `accept/`, is generated by `scripts/gen_pod_encryption_vectors.py` from one table; CI fails if they differ from a fresh generation. Do not edit them by hand.

| Kind | Where | Count | The claim |
|---|---|---|---|
| negative | `negative/N-*.json` | 64 | a header every reader MUST refuse **before deriving any key**, with the stated outcome: `malformed`, `unsupported-version` or `cannot-open`. One or more per refusal rule and per limit in sections 4, 5.1 and 5.3. |
| accept | `accept/A-*.json` | 14 | a header every reader MUST open with the stated key: the rules that tell a reader what not to refuse (unknown kinds skipped, unknown members ignored, `createdAt` never parsed, duplicate salts, the header size and wrap-count limits themselves) |
| file system | described in `vectors.json` | 9 | layouts a harness builds at test time, because a repository cannot carry a FIFO, a device or a symbolic link portably: header paths that are directories, links, FIFOs or `/dev/zero`, a `settings` directory that is a link, and links inside a Pod that point out of it (sections 4.1, 5.1, 8) |

Every generated header is one mutation of a positive fixture's header, so a reader that wrongly accepts a negative vector opens it with the fixture's key. A missed refusal therefore shows up as an opened Pod, not as an ordinary wrong-key error. The vectors that change the decoded salt or wrapped key itself (a wrong length, a different alphabet) cannot keep the key working; a reader that wrongly accepts one derives a key and reports an incorrect secret, which is also a failure, because every refusal must come before derivation.

To run a header vector by hand: make an empty directory, write the vector's bytes to `settings/encryption.json` inside it, and open it as a Pod with the vector's `tryWith` key.

## Running them against an implementation

```bash
python3 scripts/check_pod_encryption.py --cascade "node /path/to/cli/dist/index.js"
```

The harness drives `cascade-cli` through its command line (no other implementation has a public adapter yet) and ratchets the result against `KNOWN_FAILURES.json` in this directory, the same way `scripts/check_baseline.py` ratchets the SHACL suite: an unlisted failure fails the run, and a listed failure that now passes also fails the run. It is not run in CI yet, because it needs a pinned build of the implementation under test.

Entries in `KNOWN_FAILURES.json` marked `"measured": false` belong to an implementation this harness cannot run. They were found by reading its code, and are listed so that its own test suite, when it runs these vectors, confirms or removes them.

Measured with `cascade-cli` 0.22.0 (built from `main` at `059a725`): 85 passed, 7 failed, 92 total; all 7 are listed.

## Regenerating

```bash
python3 scripts/gen_pod_encryption_vectors.py --write   # after editing the table in the script
python3 scripts/gen_pod_encryption_vectors.py --check   # what CI runs
```

The positive fixtures are not generated here and are not regenerated. A new fixture comes from an implementation, and the commit that adds it says which one and how.
